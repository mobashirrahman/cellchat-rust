## Method

* One warm-up run discarded (page cache cold for the multi-hundred-MB matrix).
* ≥3 timed repeats; median reported.
* Peak RSS via `gc()`, confirmed against `/usr/bin/time -v`.
* Repeat variance is 1.5–2 % warm. **Background load must be zero** — the same config
  measured 128 s instead of 84 s while another job shared the machine.

## Cost decomposition (human skin, `nboot=100`)

| stage | time | share |
|---|---:|---:|
| setup (`as.matrix`, `max`, first `aggregate`) | ~1.3 s | 1.5 % |
| **bootstrap aggregation** | **~83 s** | **92 %** |
| L-R × bootstrap loop (158 300 iterations) | ~5.5 s | 6 % |
| total | 89.7 s | 100 % |

Isolated micro-measurements (1782 genes × 5000 cells × 25 groups):

| operation | time |
|---|---:|
| `aggregate(t(X), list(g), triMean)` | **2.149 s** |
| hand-written `split` + `vapply` | **0.679 s** (3.2× faster) |
| `t(X)` | 0.309 s |
| `as.matrix(dgCMatrix)` | 0.109 s |

**Engineering consequence:** the `nLR × nboot` loop looks like the parallel target but
is ~6 % of runtime, because most L-R pairs take the `sum(P1_Pspatial) == 0` early exit on
sparse data. Effort belongs in the aggregation.

## Strong scaling (human skin, nboot = 100, Rust only)

| threads | median | speedup | efficiency |
|---:|---:|---:|---:|
| 1 | 10.58 s | 1.00× | 100 % |
| 2 | 5.72 s | 1.85× | 92 % |
| 4 | 3.52 s | 3.00× | 75 % |
| 8 | 2.16 s | **4.91×** | **61 %** |
| 16 | 2.34 s | 4.52× | 28 % |

4.91× on 8 physical cores, 61 % parallel efficiency. **16 threads is slower than 8**, which is the
SMT result and the concrete reason `parallel::detectCores()` may not be used for anything on this
host: it reports 16 for a machine with 8 cores, and a scaling table that included 16 as though it
were 16 cores would claim an efficiency the hardware does not have.

## The kernel was single-threaded until the benchmark measured it

The first version of the sweep -- taken *before* `build_boot` was parallelised -- was flat:

| threads | 1 | 2 | 4 | 8 | 16 |
|---|---:|---:|---:|---:|---:|
| median | 10.66 s | 10.59 s | 10.69 s | 10.63 s | 10.70 s |

Flat to within noise across a 16× thread range is not a scaling result, it is the signature of a
sequential loop, and `grep -rn "par_iter\|into_par_iter\|rayon::" crates/r-core/src/` returned
nothing: the bootstrap replicate loop was a plain `for`, and 92-95 % of runtime is bootstrap
aggregation. A `rayon` dependency, a `request_num_threads` API and a thread-pool builder were all
wired up and all unused.

Parallelising it took human skin from 8.39× to 42.14× **with no change to any output** -- the
aggregate is embarrassingly parallel, each replicate reads a disjoint permutation of the same input
and writes a disjoint slot, and `collect()` on an indexed parallel iterator keeps replicate order so
the `F80` accumulation order *within* a replicate is untouched.

The split into two phases is forced by the RNG and not by convenience. R does
`set.seed(seed.use); permutation <- replicate(nboot, sample.int(nC, nC))`, so replicate `nE`
consumes the `nE`-th slice of **one** MT19937 stream; drawing them in parallel would need one stream
per replicate, which is a different permutation set rather than a different order of the same one.
So the permutations are drawn sequentially and only the aggregation is parallel.

## What this cost to find, and what it says about the projection

The projection in this file used to be "~4 s" and "~22×" for human skin, from a cost model of
"stream 63 MB × 100 = 6.3 GB across 8 cores". The measured single-thread time is 10.58 s, so the
model was wrong twice: it assumed the streaming was already parallel when it was not, and it
underestimated the per-replicate aggregation cost by about 2.6×. The 42.14× now measured is 1.9× the
old projection, and 26.06× on the wound fixture.

The general lesson is the one the objective already states -- do not publish a multiplier before
measuring it -- and it is worth being precise about the mechanism. The projection was a plausible
model of a *sequential* kernel, written while the kernel was sequential, and it was internally
consistent; what made it wrong was that nobody had built the benchmark that would have told them
the kernel was sequential. A cost model is a hypothesis with arithmetic in it, not a measurement.

## Amdahl decomposition (human skin, nboot = 100)

Fitting `T(p) = s + (1 - s) T(1) / p` over the thread sweep gives a serial term of about 0.9 s
against a single-thread time of 10.58 s, i.e. an implied serial fraction near 8 %: the parallel part
is the bootstrap aggregation and the serial remainder is the L-R × bootstrap interaction loop, which
is already only 6 % of the sequential cost. At 8 threads that leaves the interaction loop and the
RNG as the binding constraint, which is the next thing to attack and not the aggregation.

Memory is the other roofline. The kernel streams the dense signalling matrix once per replicate --
6.3 GB for human skin at `nboot = 100`, 18.1 GB for the wound fixture -- and the 4.91× at 8 threads
is well short of linear, which is what a bandwidth-bound streaming loop looks like rather than a
compute-bound one. Peak RSS stays modest (1.3 GB, 2.4 GB) because the replicates are aggregated one
buffer at a time.

## Reproducing

```sh
cargo build --release
Rscript scripts/reinstall.sh                      # into .rlib, never the site library

# The two headline rows. SPECIES selects the database *and* the fixture's CellChatDB; the runner
# refuses to start if CELLCHATRS_DB's MANIFEST.tsv does not agree with it.
#
# The assignments go *before* `taskset`. Written as `taskset -c 0-7 CELLCHATRS_THREADS=8 Rscript`,
# taskset takes the variable assignment as the command to execute and exits with
# `failed to execute CELLCHATRS_THREADS=8: No such file or directory` -- which is what this
# section used to say, and which nobody could have run.
SPECIES=human CELLCHATRS_THREADS=8 taskset -c 0-7 \
  Rscript bench-runner/bench_real.R --fixture .../humanSkin.rda --nboot 100 --repeats 5 \
    --out bench-runner/results/human_skin.json
SPECIES=mouse CELLCHATRS_THREADS=8 taskset -c 0-7 \
  Rscript bench-runner/bench_real.R --fixture .../wound.rda --nboot 100 --repeats 5 \
    --out bench-runner/results/mouse_wound.json

# Strong scaling: --rust-only skips the R side, which does not depend on CELLCHATRS_THREADS.
for t in 1 2 4 8 16; do
  SPECIES=human CELLCHATRS_THREADS=$t taskset -c 0-7 \
    Rscript bench-runner/bench_real.R --fixture .../humanSkin.rda --nboot 100 \
      --repeats 5 --warmup 1 --rust-only --out bench-runner/results/sweep_t$t.json
done

python3 bench-runner/analyse.py --trim-scatter    # tables, Amdahl fit, parity SVGs, trim vectors
python3 bench-runner/test_analyse.py              # the analysis step's own tests
```

`--trim-scatter` runs *after* the SVGs are written and replaces each raw per-value `scatter`
vector with the summary the plot was computed from. It is part of the documented sequence on
purpose: the vectors are ~9 MB for human skin and ~40 MB for the wound fixture, and dropping them
by hand once left `parity_human_skin.svg` unreproducible from the repository, since re-running the
analysis over the trimmed file had nothing left to plot.

`analyse.py` enforces two of this document's own rules rather than trusting the runners' defaults:
it reports any result file with fewer than `5` timed repeats, and it refuses to report the
cross-fixture time-versus-cell-count fit over fewer than three points. The second guard exists
because a line through two points has R² = 1 by construction; the fit over the two headline
fixtures was reporting exactly that.

`bench-runner/fixture.R` is the CellChat input pipeline -- log1p CPM over the signalling genes,
`data.signaling` restricted to genes any L-R pair needs, `LRsig` filtered to pairs whose every
subunit is present. `prof_real.R` still holds its own copy of that preamble, because it is the
source of the recorded baselines and must not be edited into invalidating them.

Three things the runner enforces rather than assumes:

* **the database matches the fixture.** `CELLCHATRS_DB`'s `MANIFEST.tsv` is checked for both
  `species` and the pinned `upstream_commit`. The first version defaulted to `db_human`, ran the
  *mouse* fixture against the human database, and the kernel correctly returned `subscript out of
  bounds` for `TGFbR1_R2` -- whose human subunits are not in the mouse expression matrix -- while
  upstream, reading the mouse database, succeeded. It looked like a kernel bug and cost more time
  than the benchmark did.
* **the thread count is the pool size.** The runner prints `cellchatrs_threads()` -- rayon's
  *actual* pool -- and records it, because `CELLCHATRS_THREADS` is only a request. An early sweep
  reported `pool = 8` for every request from 1 to 16; the bare-session check was right and the sweep
  was not, and the difference was only visible because the number is read back.
* **memory headroom is checked before anything is quoted.** The runner refuses to report at or above
  50 000 cells unless `MemAvailable` covers `nGenes × nC × 8 B` with 60 % headroom, and prints the
  requirement and the availability either way.
* **the pinned cores are idle before anything is timed.** `bench-runner/cpu_gate.R` reads the
  runner's own CPU affinity from the kernel (`taskset -pc $$`, falling back to `BENCH_PINNED`),
  samples `/proc/stat` over a 1.5 s window, and refuses to measure if any pinned core is above
  10 % busy. All five runners use it -- `bench_real.R`, `bench_amdahl.R`, `bench_synth.R`,
  `bench_visium.R`, `bench_more_datasets.R` -- because each of their numbers is quoted somewhere,
  so "was the host quiet" is a question about all of them and not only the two headline fixtures.
  This was added after
  finding that it had to be: an unrelated `python3 gen_stats_vectors.py`
  in another project in the same account had been running at 98 % CPU for 51 hours, and the R
  median on human skin moved from
  93 s to 108 s between two runs of byte-identical code. Nothing in the artifacts said why. A
  refused run writes a `<output>.refused.json` recording the per-core busy fractions, so a
  declined measurement leaves evidence rather than silence. The fractions are recorded in
  `host_state` on every run that proceeds -- including runs that pass -- and `--allow-contended`
  (or `BENCH_ALLOW_CONTENDED=1`, for the runner with no argument parser) proceeds while still
  recording them.

  The affinity is read from the kernel rather than from an environment variable because the
  documented command never set `BENCH_PINNED`: those runs wrote `"pinned": ""` into the published
  artifact while genuinely running on eight pinned cores.

  Two bugs in this gate are worth recording because both failed *silently in the permissive
  direction*. Reading `x[1:5]` of the `/proc/stat` fields as "busy" includes `idle`, so every core
  reads 100 % and the gate refuses everything -- including an idle machine. Differencing the
  per-core busy *fractions* instead of the raw counters returns exactly 0.0 on every core: the
  counters are of order 1e9, a double resolves about 1e-7 of that, and a 1.5 s window advances them
  by only ~150 ticks, so the difference is pure rounding noise and a saturated host reads as idle.
  The gate differences raw ticks and then divides, and treats a core whose counters did not advance
  at all as *unaccounted* rather than idle. A third off-by-one had it indexing `busy[0:7]`, which R
  resolves to cpus 1..7 and never measures cpu 0 at all. All three failed in the permissive
  direction, and `tests/parity/check_cpu_gate.R` (47 checks, run in CI) reproduces each.

## Host contention: what the recorded numbers were taken under

The timings in this document were taken on a **shared** 8c/16t host, and the host was not quiet.
`who` shows three logged-in users, and the stray process described above was running throughout.
This is stated because it bounds what the medians mean, not to explain them away:

* The **speedup ratio** is far more robust than either absolute time, because `bench_real.R` runs
  upstream and the port back to back in one process on the same machine. Contention slows both sides
  in the same direction, and the observed run-to-run spread in the ratio (42.1x to 44.2x on human
  skin across two 5-repeat runs taken hours apart under different load) is smaller than the spread in
  either side's absolute time (93 s to 108 s for upstream).
* The **absolute seconds** are the weak quantity. They are reported with bootstrap CIs over the
  timed repeats, which capture the run's own noise but not a competitor that was busy for the whole
  run.
* Fresh runs now carry the evidence: `host_state.per_cpu_busy_pct` in each result JSON.

Anyone re-measuring should expect to reproduce the ratio more closely than the seconds, and should
get a quieter box than this one had.

### Do not edit a runner while it is running

`Rscript foo.R` -- and `R --file=foo.R` -- parse and evaluate a script **incrementally**. Editing
`bench_real.R` while a benchmark is running therefore changes what that running process parses
next. A wound-fixture run that had completed four of its six repeats died with

```
Error: unexpected string constant in:
"            info$n_cells, info$n_groups, info$n_genes_signaling, info$n_lr, info$nnz_pct,
            required_mb(info), if (hr$ok) ""
```

because the file on disk had been replaced underneath it by a write in progress. The error pointed
at a line that was intact both before and after, which is what makes this worth writing down: it
looks like a syntax error in committed, working code rather than a race with the editor.

Runners are therefore invoked from a snapshot of `bench-runner/`:

```sh
SNAP=$(mktemp -d) && cp bench-runner/*.R "$SNAP/" && \
  SPECIES=human CELLCHATRS_THREADS=8 taskset -c 0-7 \
    Rscript "$SNAP/bench_real.R" --fixture .../humanSkin.rda --nboot 100 --repeats 5 --warmup 1 \
      --out bench-runner/results/human_skin.json
```

The same reasoning applies to measurement hygiene generally: nothing CPU-heavy should run while a
timing run is in flight, including this repository's own test suites.

## Amdahl decomposition: where the pipeline time actually goes

`bench_real.R` measures one stage (`computeCommunProb`). That number alone cannot support a
speedup claim about the package, because a 40x kernel on a pipeline that spends half its time
elsewhere is a ~2x pipeline. `bench-runner/bench_amdahl.R` times the tutorial's full computational
pipeline stage by stage -- the same stages `tests/parity/tutorial_repro.R` proves `identical()` --
on both implementations, under the same protocol, and reports each stage's share plus the Amdahl
limit the shares imply. Raw reports: `bench-runner/results/amdahl_human_skin.json`,
`bench-runner/results/amdahl_mouse_wound.json`.

| stage | human skin R | human skin RS | speedup | mouse wound R | mouse wound RS | speedup |
|---|---|---|---|---|---|---|
| io_prep (load + CPM + createCellChat + subsetData) | 2.32 [2.30, 2.47] | 2.50 [2.35, 2.53] | 0.93x | 7.07 [6.99, 9.84] | 7.31 [7.25, 7.53] | 0.97x |
| oeg (OEG presto + OEI) | 0.92 [0.90, 0.93] | 0.92 [0.91, 0.95] | 1.00x | 3.36 [2.40, 5.15] | 2.44 [2.36, 2.84] | 1.38x |
| kernel (computeCommunProb, nboot=100) | 87.21 [78.32, 108.53] | 2.30 [2.23, 2.45] | 37.92x | 187.06 [181.14, 197.25] | 8.50 [7.99, 8.90] | 22.01x |
| downstream (filter + pathway + aggregateNet) | 0.57 [0.55, 0.71] | 0.12 [0.11, 0.12] | 4.90x | 2.51 [2.48, 2.72] | 0.44 [0.43, 0.45] | 5.64x |
| centrality (netAnalysis_computeCentrality) | 0.24 [0.24, 0.25] | 0.18 [0.17, 0.18] | 1.34x | 2.33 [2.28, 2.34] | 2.23 [2.20, 2.26] | 1.04x |
| **total / overall** | **100.1** | **6.0** | **16.66x** | **202.3** | **20.9** | **9.67x** |

Seconds are medians over 5 timed repeats (1 warm-up discarded) with bootstrap 95% CIs, taskset-pinned
to 8 cores. Peak RSS 3,289 MB (skin) / 8,922 MB (wound).

Three readings, all of which the paper needs:

1. **The kernel is 92-96% of upstream's pipeline** (96.0% skin, 92.5% wound) -- the 92-95% figure
   from the early cost decomposition, confirmed on the full pipeline rather than assumed. That is why
   a kernel-only benchmark is representative *here* and would not be in general.
2. **The honest overall number is 9.7-16.7x, not 22-42x.** The kernel speedups (37.9x/22.0x) are
   real and gated, but the pipeline a user runs includes ~10 s of I/O+prep+OEG that no kernel
   accelerates (io_prep 0.93-0.97x, oeg ~1x -- both sides run presto). The paper quotes the
   pipeline number first and the kernel number second, not the reverse.
3. **The Amdahl limit is 13-25x** (24.80x skin, 13.26x wound): even an infinitely fast kernel leaves
   the I/O+prep+OEG floor. Publishing the limit alongside the measurement is what keeps the speedup
   claim from implying more than the evidence supports -- and it is also the quantitative form of
   the downsampling correction: the floor is seconds, not hours, so subsetting cells to fit a
   runtime budget is unnecessary.

The io_prep share deserves one sentence: ~2.3 s (skin) / ~7.1 s (wound) is dominated by dense
`log1p(CPM)` materialisation, identical on both sides by construction (same preprocessing code).
It is the next bottleneck and it is an I/O-format problem, not a numerics problem.

## Synthetic grid: scaling to 50,000 cells with parity at every point

The author datasets fix nC at 7,563 and 21,557, and the multi-condition and embryonic sets add
four more sizes between 2,552 and 21,557 cells. Six uncontrolled sizes are still not a scaling
claim: nLR, nGenes and nGroups move with nC across them, so the straight line
`analyse.py` fits through the six is descriptive (R² = 0.85, negative intercept) and is labelled
as such in `scaling.json` -- it is a check that the runners behave consistently, not a model. The
downsampling correction needs evidence *above* the shipped sizes and with the other axes held
fixed -- otherwise it is an extrapolation. `bench-runner/bench_synth.R` builds synthetic datasets
on a grid of cell counts
with everything else held fixed (K=6 groups, 200 real L-R pairs from the bundled export, 320
genes with group-specific DE on 60 of them so the bootstrap finds something real, nboot=100),
times both sides under the standard protocol, and asserts `identical()` per grid point.
`bench-runner/results/synth_grid.json`.

| nC | upstream (s) | cellchatrs (s) | speedup | parity |
|---|---|---|---|---|
| 2,000 | 15.77 [15.71, 16.06] | 0.61 [0.60, 0.62] | 25.85x | identical, max diff 0 |
| 5,000 | 27.50 [22.93, 41.80] | 0.85 [0.83, 0.87] | 32.24x | identical, max diff 0 |
| 10,000 | 38.64 [38.38, 38.96] | 1.25 [1.23, 1.28] | 30.89x | identical, max diff 0 |
| 20,000 | 60.93 [60.08, 61.80] | 2.18 [2.10, 2.26] | 27.92x | identical, max diff 0 |
| 50,000 | 127.27 [126.77, 147.10] | 4.66 [4.58, 4.86] | 27.31x | identical, max diff 0 |

Log-log slope against nC: **0.637 upstream, 0.639 shim** -- the same complexity profile to three
figures, which is itself evidence the port does the same work rather than less of it. The slope
is sublinear because per-pair fixed costs dominate at these sizes, on both sides equally.

Two protocol points matter more than the table. First, the 50k point passed the enforced
memory-headroom gate (440 MB dense buffer x3 safety factor against MemAvailable) before running;
without the gate a 50k number from a swapping host would measure the page cache, not the kernel.
Peak RSS for the whole grid run was 2,489 MB. Second, bit-identity does not degrade with size:
every point is `identical()` on the full array, so no accumulation order in the port only shows
at scale.

R-side plumbing over already-computed nets (`rankNet` comparison returns plots, so parity is on
the `signaling.contribution` data frames, not the ggplot objects).

Three things the deposited objects taught the harness, recorded because each cost a failed run:

* `@<-` on a deserialized object fails. Slot assignment triggers a class-package lookup for
  "CellChat" (baked in at serialization time) that fails when only the globalenv definition
  exists -- a path no gate had exercised, since every existing test either builds objects via
  `createCellChat` or only reads slots. The benchmark rebuilds objects slot-by-slot through
  `methods::new` (`rehome()`), verifies every readable slot identical, and never assigns to a
  deserialized object.
* Old objects predate `options$datatype` (NULL) and carry non-conforming slots (E13's
  `var.features` is a bare character where the class wants a list). Both are version
  artifacts, not data problems: datatype is set to the factual "RNA" post-rehome, and
  non-conforming slots are left at defaults and recorded (`rehome_skipped_slots`), since the
  kernel never reads them.
* The deposited NL/LS objects bundle an older CellChatDB (complex table 339x5) than the pinned
  export (338x6). Exactly one pair (`IL2_IL2RA_IL2RB_IL2RG`) resolves under the former but not
  the latter -- upstream reads subunits from the object's DB and succeeds, the shim reads the
  pinned export and (correctly) raises the missing-subunit error. The benchmark runs the
  492-pair intersection both agree on and records the dropped pair (`dropped_pairs`), mirroring
  the visium benchmark's 134 resolvable pairs.

The downsampling correction, quantitatively: the full 50k-cell kernel runs in 4.7 s. Upstream's
advice to subset cells to fit a runtime budget buys nothing here -- the entire dataset that the
advice would discard runs faster than the subset it recommends keeping.

## Spatial: the exact k-d tree against `AnnoyParam`, on real data

The one place the port is deliberately *not* bit-identical to upstream is the spatial KNN query.
`computeRegionDistance` finds neighbours with `BiocNeighbors::queryKNN(..., BNPARAM = AnnoyParam())`
— twice, a 1-NN from group *i* into group *j* and a *k*-NN per sample for `adj.contact.knn` — and
Annoy is a randomised approximate index. The locked decision (`PLAN.md` §14.5) is to replace it with
an exact k-d tree and **measure** the divergence. This is that measurement.

`bench-runner/measure_spatial_divergence.R`, on the authors' own mouse cortex visium dataset:
**1,073 spots, 648 genes (433 signalling), 437 L-R pairs, 8 cell types of 23–400 spots, `nboot = 100`**,
`k.min = 10`, `contact.range = 65` (the spot diameter), `interaction.range = 1000`, `ratio = 1`,
`tol = 0`. Record in `bench-runner/results/spatial_divergence.json`.

| comparison | `d.spatial` | `Prob` |
|---|---|---|
| exact k-d tree vs Annoy | **42 of 64** entries differ (14 both-`NaN`, 50 comparable), max relative difference **2.8%** | **1,682 of 8,576** differ (**19.6%**), max absolute 0.00178, **1.0% of the peak** interaction weight |
| **Annoy vs Annoy, same input** | **0 of 64** differ | **0 of 8,576** differ |

### Annoy is deterministic here, so this is a bias and not noise

The two Annoy runs are the control, and they are what make the comparison worth anything. A difference
between two things is only evidence of an improvement if you also know which one is right.

The header of the measurement script predicted the *opposite* of what happened, and the prediction is
recorded rather than quietly removed: Annoy in `BiocNeighbors` 3.18 gives **bit-identical** results on
repeated runs over the same input. So the divergence from the exact tree is a **systematic bias**, not
run-to-run variance.

That distinction is the whole argument, and it goes the other way from the one usually made. Noise is a
variance problem and averaging fixes it. A bias is a correctness problem: a *reproducible wrong answer*
is worse than a varying right one, because nothing in a user's workflow would ever surface it. A user
re-running the same CellChat spatial analysis gets the same `Prob` every time, and every one of those
19.6% of entries is wrong by up to 1% of the peak interaction weight with no indication that anything
is off. The exact tree is a correction, not a de-noiser — and the correction is also **274× faster**
for the same `d.spatial` (0.0085 s against 2.34 s), because a two-dimensional exact k-d tree over
1,073 points is not a problem an approximate index was needed for.

### `Prob` is 1% different, not 19% different in magnitude

The fraction of *entries* that differ (19.6%) and the size of the difference (1.0% of peak) are
different claims and the paper must use both. `P.spatial` is `1/d.spatial` with the diagonal
overwritten, so a 2.8% error in a nearest-neighbour distance becomes a proportionally smaller error
in a product that is then combined with the Hill function and thresholded. A reader shown only "19.6%
of entries differ" would conclude the port is materially different; a reader shown only "1%" would
conclude it is immaterial. Both are true of different quantities and the honest summary is: a fifth of
the interaction weights move, each by at most about one percent of the strongest interaction.

### `ratio` and `tol` are not optional, and their absence is silent

Worth recording because it cost the most time. `computeRegionDistance`'s signature is

```r
computeRegionDistance(coordinates, meta, interaction.range = NULL, ratio = NULL, tol = NULL, k.min = 10, ...)
```

and with the documented defaults the body does

```r
qout$distance <- qout$distance * ratio[k]
...
d.spatial[i,j,k] <- FunMean(qout$distance)
```

`numeric(0) * NULL` is `numeric(0)`, `FunMean(numeric(0))` is `NaN`, and so **every entry of
`d.spatial` is `NaN`**. No error, no warning — a 64-element matrix of `NaN` that flows into
`P.spatial[is.na(d.spatial)] <- 0` and silently zeroes every spatial weight, so the run looks like it
worked and every communication probability is a pure expression term. `updateCellChat` normally fills
these in as `spot.diameter / fullsize`, but a visium object from before the `spatial.factors` rename
does not have them, and `ratio = 1, tol = 0` is the neutral choice for a comparison in image-pixel
units. The measurement supplies them explicitly, and the JSON records them.

`contact.dependent = TRUE` also has no default range: upstream stops with *"Please check the
documentation of `computeCommunProb` and provide the value of either `contact.range` or
`contact.knn.k`"*. That one at least raises.

### The unfiltered L-R table raises on this data, identically on both sides

`visium.rds` carries all 437 pairs from the pinned `CellChatDB`, but only **134** of them have every
receptor subunit present in the object's 433 signalling genes. On the unfiltered table both the exact
kernel and pinned upstream stop with `subscript out of bounds` — upstream's own crash for a complex
with a missing subunit, which the port is required to reproduce rather than paper over. Verified
identical, and recorded in the JSON as `unfiltered_lrsig.errors_identical`. The `Prob` comparison above
therefore runs on the 134 resolvable pairs, which is stated rather than left implicit.
